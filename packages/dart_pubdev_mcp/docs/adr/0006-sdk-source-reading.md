# SDK source reading via download-only GitHub tarballs

`dart-pubdev-explorer` gains source-reading access to Dart SDK and Flutter SDK/framework code through three new tools — `get_sdk_source_slice`, `list_sdk_source_files`, `get_sdk_throw_statements` — that mirror the existing pub.dev source-reading trio exactly, but read from version-pinned `codeload.github.com` tarballs instead of pub.dev tarballs. Acquisition reuses the `TarballDiskCache` LRU pattern unchanged; AST access reuses `AstAccess` unchanged. Scoped to **source-reading only**: no dartdoc-style symbol index (`browse_api_symbols`, `find_symbols`, `get_symbol_documentation`, `get_api_diff`) for SDK code in this pass — see Consequences.

## Context

Neither the Dart SDK (`dart:core`, `dart:async`, …) nor the Flutter SDK/framework (`package:flutter`, `flutter_test`, …) is published on pub.dev, so none of the existing tools can reach their source — the motivating case is a symbol lookup (`TestPlatformDispatcher.accessibilityFeaturesTestValue`), not a line-range read. Both SDKs are structurally the same problem (source not on pub.dev) and are decided together here so the design doesn't need revisiting when the other is requested.

Settled during charting, before any ticket work (`issues/sdk-source-reading/Map.md` Notes) and treated as fixed constraints below:
- Version resolution auto-detects from the environment, with an explicit override parameter always available.
- New, separate tools — not an overload of `get_source_slice`/`list_package_source_files`'s `package`/`version` parameters, which are documented and typed around pub.dev packages.
- Both line-range and symbol-bounded (AST) reads from day one.
- Caching reuses the `TarballDiskCache` pattern.
- `AstAccess` (`lib/src/analysis/ast_access.dart`) needs no SDK-specific changes — its `member`/`unit`/`fileText` API only needs a path→content map for a given `(name, version)` key; whichever acquisition strategy is chosen only has to produce that map.

Full decision trail: `issues/sdk-source-reading/` — one research ticket and four grilling tickets, summarized below.

## Decision

**Acquisition: download-only via `codeload.github.com`, identical mechanism for both SDKs** (`issues/sdk-source-reading/02-decide-acquisition-strategy.md`). Always fetch a version-pinned tarball — `https://codeload.github.com/dart-lang/sdk/tar.gz/refs/tags/{ref}` (or the equivalent commit-SHA path when `ref` is a SHA) for the Dart SDK, `https://codeload.github.com/flutter/flutter/tar.gz/refs/tags/{ref}` for Flutter — cached through the reused `TarballDiskCache`, mirroring the existing pub.dev package pipeline exactly. Local disk is still read, but only for cheap default-version-detection metadata, never for source content: `dart:io Platform.version` for the Dart SDK (zero subprocess calls, zero file reads — the MCP server is itself a Dart process), and a local `flutter.version.json` read (via `FLUTTER_ROOT`/`PATH`) for Flutter.
- *Rejected — local-disk read as the primary source, download as fallback*: research confirmed a local install's `packages/flutter/lib/src/**` and `bin/cache/dart-sdk/lib/**` do contain full, real source. Rejected anyway — this package's existing tarball pipeline already always downloads its own copy from pub.dev, never reading the user's local pub cache even though one exists; download-only keeps that precedent and keeps behavior identical regardless of what happens to be installed on the host.
- *Rejected — hybrid (local when available and version-matching, download otherwise)*: the version-matching and fallback logic isn't worth the complexity given download-only already covers every case the research turned up.
- *Rejected — splitting the mechanism between the two SDKs*: research found no real asymmetry — both are git-checkout-backed repos with working `codeload` tarballs of equivalent size (32–37 MB compressed).

**Path normalization** (`02-decide-acquisition-strategy.md`). The raw `dart-lang/sdk` repo tarball is shaped `sdk/lib/core/...`, not the installed/built SDK's `lib/core/...`. The Dart SDK tool surface normalizes to the installed-style shape, stripping the tarball's `sdk/` prefix at lookup time — this matches `dart:core`'s conceptual shape and decouples the tool's public path contract from GitHub's repo layout. Flutter needs no equivalent normalization: the `flutter/flutter` tag tarball's `packages/flutter/lib/src/...` layout already matches the installed layout exactly.

**Cache key scheme, `TarballDiskCache` unchanged** (`issues/sdk-source-reading/04-cache-key-scheme.md`).
- Dart ref: `Platform.version.split(' ').first`, used verbatim as the `dart-lang/sdk` tag. Verified live against `codeload.github.com` across all three channels (`3.12.2` stable, `3.13.0-282.2.beta` beta, `3.14.0-41.0.dev` dev) — no channel branching needed.
- Flutter ref: `flutter.version.json`'s `frameworkVersion` by default, or the explicit override.
- Cache key: `name` = a literal, fixed per-SDK string (`dart_sdk` / `flutter_sdk`), `version` = the resolved ref as-is. Both pass `TarballDiskCache`'s existing charset validation (`^[a-zA-Z0-9_]+$` for `name`, `^[0-9a-zA-Z.+_-]+$` for `version`, which already accepts a commit SHA) unchanged — no changes needed to `TarballDiskCache` itself.
- *Dropped as moot — bundled-vs-standalone Dart SDK identity inside a Flutter checkout*: `sdk: 'dart'` and `sdk: 'flutter'` each resolve their own default version independently, always the same way; `flutter.version.json`'s `dartSdkVersion`/`dart-sdk` `revision` fields are never read for `sdk: 'dart'` requests. There is no "Flutter-detected context" branch.

**`AstAccess` is reused as-is** — no SDK-specific subclass or parsing logic. The new acquisition path only needs to produce a path→content map for a given `(name, version)` cache key, fed into a second `KeyedCache<SourceFilesId, Map<String, String>>` instance (distinct store from the pub.dev one, same shape) and a second `AstAccess` built over it.

**Tool surface: three new tools, an `sdk` selector, no per-SDK duplication** (`issues/sdk-source-reading/03-tool-surface-design.md`).
- **`get_sdk_source_slice`** — mirrors `get_source_slice`'s dual mode exactly (line-range via `lineStart`/`lineEnd`, or symbol-bounded via `symbolName`, with `maxLines` truncation). Parameters: `sdk` (`'dart' | 'flutter'`), `library` (Dart) or `package` (Flutter), `file`, `version` (optional override), plus `lineStart`/`lineEnd`/`symbolName`/`maxLines`.
- **`list_sdk_source_files`** — mirrors `list_package_source_files`. Parameters: `sdk`, `library`/`package` (optional filter, same role as today's `directory`/`fileExtension` filters), `version`.
- **`get_sdk_throw_statements`** — mirrors `get_throw_statements`'s scope semantics (`class`/`method`/both/neither). Parameters: `sdk`, `library`/`package`, `class`, `method`, `version`. Its top-level-function resolution differs from the pub.dev tool — see the dedicated decision below.
- **No `get_sdk_symbol_documentation`, `browse`, `find`, or `diff` tool** — dartdoc-index tooling, deferred per Out of scope.
- *Rejected — separate tools per SDK* (e.g. `get_dart_sdk_source_slice` / `get_flutter_sdk_source_slice`): doubles the tool count for what the research confirmed is one structurally identical problem; the `sdk` selector keeps the trio at three tools total.

**Parameter naming: `library` for Dart, `package` for Flutter** (`03-tool-surface-design.md`, amendment). `sdk: 'flutter'` takes values like `'flutter'`, `'flutter_test'`, `'flutter_driver'` (resolving to `packages/<name>/lib/...`); `sdk: 'dart'` takes a `dart:` library name — `'core'`, `'async'`, `'io'`, … — mapped internally to the installed-style subpath.
- *Rejected — a uniform `package` name for both*: several `dart:` library names (`'async'`, `'collection'`) collide with real, independently-versioned pub.dev packages published by the Dart team. `package` for Dart never drove cache/version selection the way it does for a real pub.dev package — every `dart:` subdirectory ships from the same single SDK checkout at the same version — so it was a subdirectory selector wearing a heavier, collision-prone name than it needed. `library` is also the term Dart itself uses (`dart:core` *library*), so this is more accurate, not just less collision-prone. Flutter's `package` is unchanged — `packages/flutter`, `packages/flutter_test`, etc. are real packages, each with its own `pubspec.yaml`.

The `version` override parameter is named `version` — reusing the existing pub.dev-tool convention rather than an SDK-specific name — with the same optional/override semantics (omit to auto-detect via `Platform.version` or `flutter.version.json`).

**`get_sdk_throw_statements`'s top-level-function resolution cannot reuse the `apiIndex` facade** (new design point, surfaced while writing this ADR — not covered by any ticket). The existing `get_throw_statements`, when `class` is omitted and `method` is provided, disambiguates candidate top-level functions via the shared `apiIndex` `KeyedCache` facade (the same dartdoc symbol index `browse_api_symbols`/`find_symbols` use) before scanning. That facade is explicitly out of scope for SDK code this pass (Map Out-of-scope). The `class`-provided path, by contrast, already needs no index — it scans `AstAccess.sourceFiles()`'s file map directly, file by file, until the class is found (`_MethodScanResult`'s `classFound` flag).
- Decision: `get_sdk_throw_statements`'s method-only case adopts the same file-by-file scan the class-scoped case already uses, applied across every file in the selected `library`/`package`'s source map. Zero matches → `SYMBOL_NOT_FOUND`; more than one top-level match across files → `AMBIGUOUS_SYMBOL` with `error.details.candidates` (same shape the pub.dev tool already returns). This makes `get_sdk_throw_statements` fully independent of any symbol index, consistent with the Map's Out-of-scope boundary — at the cost of a linear per-call file scan instead of an indexed lookup. Accepted: SDK libraries/packages are bounded in file count (tens to low hundreds of `.dart` files per `library`/`package`), and every file is already being pulled from a warm `sourceFiles` cache entry, not re-downloaded or re-parsed from scratch per scan.

**Error handling** (`issues/sdk-source-reading/05-error-handling-fallbacks.md`).

| Case | Code | Retryable |
|---|---|---|
| Failed/truncated `codeload.github.com` download | *(none — reuses `RetryPolicy`/`HttpStatusException` verbatim)* | per existing policy |
| Unparseable `Platform.version`, or resolved version has no matching tag/commit (either SDK, incl. explicit override typos) | `SDK_VERSION_NOT_FOUND` (`details.sdk` distinguishes `dart`/`flutter`) | no |
| No local Flutter install detected, no explicit override given | `SDK_NOT_DETECTED` | no |

`_downloadBytesWithLimit` (`lib/src/data/pub_client.dart`) already buffers a full response in memory under a byte cap and deadline before ever calling `TarballDiskCache.write`, and `write()` itself uses temp-file-then-rename with cleanup on `FileSystemException` — a partial/truncated download therefore never reaches the cache as a partial write regardless of source repo, so the `codeload.github.com` download path needs no new partial-write handling. An unparseable or untagged version is not specially validated up front for either SDK — it is left to surface as the natural `codeload.github.com` 404 at fetch time, now given its own `SDK_VERSION_NOT_FOUND` code distinct from pub.dev's `PACKAGE_NOT_FOUND` (the user-facing framing differs: "no SDK release matches this version," not "package not found"). No Flutter install found and no override is a distinct failure mode — not that a version doesn't exist upstream, but that no default version could be determined locally — and does **not** fall back to shelling out to `flutter --version` on `PATH`: spawning a process and parsing free-text CLI output is fragile and slow just to recover a version the caller can supply directly via `version`, and keeps SDK version-detection purely file-based.

## Consequences

- Two new `DomainErrors` codes: `sdkVersionNotFound` = `'SDK_VERSION_NOT_FOUND'`, `sdkNotDetected` = `'SDK_NOT_DETECTED'`. Neither is added to the `_retryable` set. `docs/adr/0002-error-schema.md`'s code registry table gains both rows.
- New modules (sketch, not prescriptive — implementation tickets to follow): an SDK tarball acquisition component parallel to `PubDevClient`'s existing tarball path, producing a path→content map per `(sdk, resolved ref)`; a second `KeyedCache<SourceFilesId, Map<String, String>>` store and a second `AstAccess` instance built over it; three new tool handler files (`get_sdk_source_slice.dart`, `list_sdk_source_files.dart`, `get_sdk_throw_statements.dart`) mirroring the existing trio's structure; `CacheRegistry` wiring for the two new caches.
- The pub.dev tools' `latest` sentinel for `version` has no SDK equivalent — there is no "latest stable" resolution endpoint for a git repo the way pub.dev exposes one for packages. Omitting `version` triggers auto-detection (`Platform.version` / `flutter.version.json`) instead of a "latest" lookup; passing the literal string `'latest'` is not special-cased and surfaces as `SDK_VERSION_NOT_FOUND` like any other unmatched ref.
- Full parity with the existing pub.dev dartdoc-style symbol index (`browse_api_symbols`, `find_symbols`, `get_symbol_documentation`, `get_api_diff`) applied to SDK code remains a **deliberately deferred future option**, not built now. Should it ever be pursued, `get_sdk_throw_statements`'s per-call full-subtree scan would likely be superseded by an indexed lookup at that time, and the acquired-but-unused parts of an SDK tarball (docs, tests, tooling outside `lib/`/`packages/*/lib/`) become relevant for the first time.
- Full decision trail and research asset: `issues/sdk-source-reading/`. Implementation is not yet ticketed.
