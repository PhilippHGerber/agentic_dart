After — one deep envelope module

ToolResponse

resolvedVersion-first invariant + isError mapping live here, once

Problem: the DomainError → CallToolResult(isError: true) mapping is one concept implemented as 12 identical private _domainError adapters, and the "resolvedVersion is the first key" invariant is enforced by comment in ~9 separate _success builders.

Solution: a ToolResponse module with a two-method interface — ok() and error() — that owns the Tool Error envelope (ADR-0002) and the Resolved Version placement; delete all 12 copies.

  • locality: envelope changes touch one module
  • leverage: one interface, 66 call sites
  • resolvedVersion invariant becomes code, not comments
  • deletion test: complexity concentrates, clearly
Aligns with ADR-0002 — same wire schema, finally with a single implementation. No conflict.

Problem: "if version supplied use it, else log + resolve Latest Stable Version + on failure return the Tool Error" is re-implemented in 9 handlers in three different spellings, including a hand downcast (as PubDevSuccess<String>) that pattern matching should make impossible.

Solution: one VersionResolver module (or handler-base method): resolve(name, suppliedVersion) → PubDevResult<String>. The logging line and failure path move behind the interface.

  • locality: resolution bugs fix once, fixed 9×
  • leverage: get_api_diff's double-resolve comes free
  • downcast smell deleted
  • tests: resolution tested once at its interface
ADR-0004 keeps the caching below the client seam — this resolver adds no cache, so no conflict.

Worth exploring
in-process

Before — every handler re-answers "how do I read an argument?"

args['package'] as String? ?? '' · inline check · own INVALID_ARGUMENT literal
args['limit'] as int? ?? 10 · limit > 25 check inline
required-field emptiness check · own literal
… ×12 handlers, each its own dialect

After — one deep extractor

ToolArgs

requiredString('package')
intInRange('limit', 1, 25)
→ PubDevResult<T>

parse + validate + INVALID_ARGUMENT construction, behind one interface

Problem: argument parsing and validation is a shallow ritual repeated 12×; each handler builds its own INVALID_ARGUMENT DomainError literal, so message wording and validation strictness drift per tool.

Solution: a small typed extractor over request.arguments returning PubDevResult, so failures flow into the same envelope as every other Tool Error.

  • locality: validation wording drifts nowhere
  • leverage: one interface, 12 handlers
  • composes with candidates 1 and 2

Top recommendation

1 · One home for the Tool Error envelope

It is the widest duplication (12 modules, 66 call sites), the most mechanical to land, and it creates the seam that candidates 2 and 3 plug into — both version resolution and argument validation end by producing exactly this envelope. Land it first and the other two deepenings become small diffs instead of medium ones.
